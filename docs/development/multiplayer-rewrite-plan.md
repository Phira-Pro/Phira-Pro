## 兼容边界

首版保留原协议的 TCP 连接、版本字节 1、ULEB128 帧长、命令编号与字段顺序。单帧 payload 上限 2 MiB，另外限制长度前缀、集合数量及累计分配。未知基础命令报协议错误并断开；已知命令的帧尾字节保留或跳过，不能误读为下一帧。

先鉴权、再开始正常心跳；依据版本常量，ping 间隔 3 秒、等待 2 秒，实际重连策略单独定义。RPC 先注册后发送；同种旧 RPC 禁止重叠。超时保留未决状态并停用该连接，通过新连接恢复，不在旧连接直接重复开局或成绩提交。

不主动发送未协商的额外命令或虚构 trailer 标准。服务端未来声明扩展能力后，才能启用请求 ID、完整快照、资源确认、回合绑定等增强路径。基础协议没有这些能力时，在 UI 和日志中保留未知状态。

自定义地址首先支持 `host:port`、域名、IPv4 及 `[IPv6]:port`；协议类型与端口显式校验，不猜测其他服务的 HTTP API。换服务端时关闭原连接并隔离旧任务。旧协议是明文 TCP，诊断日志不能输出 token 或完整鉴权包。

## 模块划分（拟新增，非现有 API）

| 模块 | 职责 | 不应承担的工作 |
| --- | --- | --- |

| `mp/transport` | TCP、有界收发、连接截止、心跳、连接代次 | 房间业务和游戏启动 |
| `mp/session` | 唯一会话所有者、RPC、顺序事件处理、鉴权与重连 | 绘制面板、直接创建 GameScene |
| `mp/room` | 房间快照、选曲、准备、成员、回合和启动记录 | 网络写入、下载文件 |
| `mp/resources` | 从匹配的资源服务查谱、下载、版本校验、取消旧下载 | 决定房主权限 |
| `mp/game_bridge` | 本局规则副本、启动、回放/实时回调组合、结果归属 | 保存或修改用户全局判定预设 |

| `mp/panel` | 服务器、建房入房、成员、聊天、准备、错误/重连显示 | 根据最后一帧阶段猜测漏掉的事件 |

先放在 `phira/src/mp/`，协议/会话逻辑不依赖图形资源。若后续需要 SDK 或服务端共用，再抽取独立 crate，不提前制造跨 crate 耦合。

## 状态与生命周期

1. 所有收包与 RPC 结果经单一会话执行器处理，安装鉴权/入房快照之后再完成对应调用；调用方不再二次写房间状态。
2. 用顺序事件更新唯一房间模型，UI 仅观察快照。即使一帧收到选曲、等待、开局，谱面也在选曲事件到达时保存，不依赖 UI 看见中间画面。
3. 资源任务绑定连接代次、房间代次、选曲代次。换谱、离房、换服后，旧下载和入房任务结果不得覆盖当前选择或发送 Ready。
4. “收到选曲”“资源下载完成”“场景加载完成”“已启动”“已完成待报告”分别记录。缺谱、损坏、选择不明时不给出本地准备成功，也不启动旧谱。
5. 启动凭据在本地记录已消费状态。重复 Playing 不重复启动；一局结束后的临时阶段变化不能自动重开同局。旧协议无 round_id，不能以本地计数冒充服务端回合证明；遇到歧义停止自动开局并恢复连接/提示用户。
6. 会话运行不依赖面板展开或主场景是否位于栈顶。游戏和面板使用同一共享会话句柄，不各自维护一份重连 Client。
7. 离房、断线、应用后台与恢复明确区分；应用被系统挂起时不假定网络仍然活跃。恢复后先核对会话和资源，不重放旧开局。
8. 完成报告保存连接/房间/谱面/本局标识及记录来源；成功、失败、未决分别展示。超时不直接删除报告，也不跨回合盲重试。

## 必须解决的两项互操作问题

### 身份、资源与成绩来源

已核对原服务端通过 `HOST/me` 校验 token，通过 `HOST/record/{id}` 查询 Played 记录，并校验 player。原 token 字段最多 32 字节。Pro 的 JWE 不能假定符合这一长度或被该身份服务接受。

Pro 当前成绩只发往 `/api/v1/scores`。Pro 记录 ID 即便数值碰巧存在于官方，也不表示同一记录。必须使用带来源的 `ResultProvider`，并校验用户、谱面与本局；不能沿用全局 `RECORD_ID` 作为联机完成证据。

用户已确定不接入官方成绩上传，采用以下策略：

- **Pro 成绩路径**：正常完成后显示实际结算，按 Pro 现有计分资格保存本地成绩和回放，符合条件时上传 Pro。上传失败不阻塞结束联机参与，也不回退官方上传。主动退出仍记为本地退出，不能伪造正常成绩。
- **官方联机兼容路径**：无论正常完成后返回还是主动放弃，都在合适的游戏返回时机发送一次真实 `ClientCommand::Abort`，接收其匹配响应。正常完成的本地状态仍为 Completed，网络结束方式单独记为 AbortFallback；不发送 `Played`，不提供任何 Pro 记录 ID。官方房间会将该参与者视为放弃，不能承诺官方联机榜单显示其本局分数。
- **自有/第三方增强路径**：只有服务端明确支持 Pro 记录来源或双方约定的成绩接口后，才启用对应结果上报。仅更改 TCP 地址不能证明支持 Pro 成绩，也不能自动猜出 HTTP 成绩接口。不具备该能力的基础协议服务端使用明确配置的 Abort 兼容策略。

本地结算、Pro 上传任务和联机参与结束分别记账。不得因为 Pro 上传失败把本地完成改成退出，也不得因为 Abort 成功把成绩标成“已提交官方”。联网 UI 应简短说明“本局成绩保存在 Pro，当前联机服务端按放弃结束”。

结束任务绑定连接代次、房间及本局上下文，阻止重复发送和跨局迟到操作。Abort 响应丢失时标记未决并按会话恢复策略核对状态，不在已进入下一局的连接盲目重试。官方兼容路径应验证服务端能结束当前回合并继续下一局；它是用户接受的降级方案，不是官方成绩互通。

选择相同 chart ID 也必须来自同一资源命名空间。首版不承诺本地私谱 P2P 分享，不用 MP 地址推断下载来源；资源 API 不匹配时应说明原因。

### 判定与实时流

基础 Judgement 仅有 Perfect、Good、Bad、Miss、HoldPerfect、HoldGood。PERFECT+ 在基础流中归并为 Perfect（Hold 按实际持有/结束事件语义处理），本地回放仍保留原始档位。GREAT/OK/MEH 无原协议直接对应，不能私自加枚举编号。

公平联机首版应采用显式统一的判定与玩法策略；具体选用哪套规则需要在编码前定下，不默认沿用玩家个人预设，也不把 `force_official_play` 等同于 Phigros 本家判定。背景模糊、皮肤等纯显示偏好保留。

触点映射必须独立于平台原始 finger ID，用受限的 i8 映射并按旧协议编码结束事件；不能把现有回放的触点 ID 直接截断。实时发送有界、批量且不阻塞渲染。消费外部判定时校验时间有限值与行/音符索引，异常隔离至来源玩家；合法索引不能证明谱面匹配。

## 实施顺序与验收

1. 协议与会话：完整编解码、回环假服务端、鉴权/心跳/RPC、错误断连；不先做空壳面板。
2. 房间与资源：创建/加入/离开、房主/成员、锁房轮换、选曲准备、下载失败和取消、逐事件状态管理。
3. 游戏与成绩：按已确定的 Pro 成绩 + 官方 Abort 兼容策略，双客户端完整走通准备→游玩→本地结算→回房→下一局；组合回放记录与 live 回调，另行确定统一联机判定规则。
4. UI：自定义地址、房间操作、聊天和恢复状态；遵循现有 Phira UI/面板动画与 HUD 安全区域。
5. 桌面和移动端回归，再按本地交付约定构建 Windows 包；发布需要用户另行指示。

验收覆盖指引 T01–T10，但新客户端应断言安全处理，而非仅证明旧实现的 panic。特别覆盖：

- 入房响应紧跟阶段推送、快速响应早于调用方继续执行；同种请求重叠、超时迟到和重复响应。
- 一帧多阶段、后台恢复、加入旧结果覆盖、换谱时旧下载完成、缺资源开局。
- 已完成玩家不重开、回房继续第二局、房主离房、重连后同一会话承接成绩。
- TCP 分片/粘包、超长/截断/未知枚举、已知命令帧尾扩展。
- 触点生命周期、PP 降级映射、外来索引越界、live 拥塞不拖慢游玩。
- 官方兼容模式正常完成后，本地成绩/回放仍保留，服务端仅收到 Abort 而非 Played；主动退出的本地状态仍不同于正常完成。
- Pro 上传失败时仍能结束联机参与；Abort 重复、超时、迟到与换局不误伤下一局；完成降级后可继续第二局。
- 成绩 ID 来源不匹配、提交失败与未决状态；只有明确支持 Pro 成绩的服务端才启用相应结果提供方。
