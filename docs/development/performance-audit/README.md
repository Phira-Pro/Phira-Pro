# Phira-Pro 性能审计总览

- 文档版本：2.0
- 基线仓库：Phira-Pro
- 基线分支：`main`
- 基线提交：`0e33da13294fd3b3d715f1fd00c45b3f1610859c`
- 基线日期：2026-11-11
- 适用对象：准备把优化移植到 Phira-Pro `main` 的实施工程师、负责质量与性能验收的评审人、维护渲染与加载路径的维护者、以及需要判断某项结论是否还能作为决策依据的审计人
- 文档集：本文件、`positive-optimizations.md`、`non-positive-optimizations.md`、`library-level-optimizations.md`、`appendix-mainline-integrated.md`、`appendix-methodology.md`

本文是一份“待实施清单”，不是“研究成果陈列”。它只回答三个问题：

1. 哪些优化在 Phira-Pro `main` 上还没有完成，因此仍值得投入。
2. 每个候选的判定、参考实现状态、证据强度、风险和验收门槛是什么。
3. 一项优化真正完成主线合入与验收后，文档里应该留下什么可追溯记录。

本文不替代代码审查，也不替代真机复测。它把判定口径、状态口径、证据边界和验收流程固定下来，让后续工程师不必依赖某次本地研究、某份日志或某个已经离开的人。

## 1. 一句话口径

- `☑ 已实施（main）` 的唯一含义是：改动已经合入 Phira-Pro `main`，并且完成了质量验收与性能验收。
- 本地参考实现、能编译、参考实现默认开、真机跑过对照，都不构成 `☑ 已实施（main）`。
- 本文只讨论“主线尚未实施”的优化；已经进入 `main` 的早期优化只放在 `appendix-mainline-integrated.md`，不进入本文的总索引。

一句话记忆：**main 合入 + 验收通过 = 可以勾选；其他情况一律保持未勾选。**

这条口径比旧版更窄，也更适合工程决策。参考实现的价值是证明“这条路走得通、代价有多大、画面是否保真”，不是证明“主线已经拥有这项优化”。读者看到 `☐ 未实施（main）` 时，不应据此认为参考实现不存在；读者看到“参考实现状态：完整”时，也不应据此认为主线已经完成。

## 2. 范围

### 2.1 纳入范围

- Phira-Pro `main` 尚未合入或尚未完成验收的渲染、加载、字体图集、block 效果、谱面解析与库级优化。
- 已经有参考实现、真实消费者、同 SO 对照或明确失败证据的候选；包括正优化、无优化、负优化和未完成项。
- 与普通游玩、加载、结算、HUD、字体图集、透明判定线、block overlay 直接相关的 CPU 与 GPU 工作。
- 在真机 Android 上取得的性能、像素和稳定性证据；证据必须写明设备、画质、窗口、轮次和样本数。
- 为了让上述优化可实施而做的库级改动，例如 macroquad 与 miniquad 的批处理、资源寿命、纹理上传和 uniform 缓存。
- 参考实现默认关闭、但仍值得保留的候选；它们的主线状态仍是 `☐ 未实施（main）`，参考实现默认写“关”。

### 2.2 排除范围

- `rpe-next` 项目及其编辑器、协作服务器、桌面端性能工作。它不属于 Phira-Pro 的渲染栈，数据不能与本文档混用。
- 已经进入 Phira-Pro `main` 的早期优化。它们统一放在 `appendix-mainline-integrated.md`，不计入本文的总索引与统计。
- 后端、多人联机、账号、成绩上传、RPEN 编辑器功能本身。
- 通过降低分辨率、MSAA、粒子数量、效果采样数、纹理精度或隐藏画面来换取的“性能提升”。本审计的口径是保持画质；降低画质不是本文讨论的优化。
- 只有设计草案、没有代码、没有真实消费者、没有测量的想法。纯提案和纯测量都不进入 P/N/L 条目。
- 上游库自身的通用性能改进，除非它以固定 rev 的形式进入了 Phira-Pro 的候选路径。
- 只存在于本地日志、一次性脚本或不可达提交中的“看起来更快”，不能作为条目证据。

### 2.3 基线与时间

- 本文件以 Phira-Pro `main` 的 `0e33da13294fd3b3d715f1fd00c45b3f1610859c` 为基线，基线日期为 2026-11-11。
- 参考实现的主要测量集中在 2026-10-05 至 2026-10-24。2026-10-24 之后研究暂停，未完成项保持未完成，不因时间推移自动变成“完整”。
- 本文件不把“参考实现能编译”当成“主线已经合入”，也不把“参考实现默认开”当成“主线已经验收”。
- 本文件不假设参考实现可以直接 cherry-pick 到当前 `main`。接口、配置字段、场景栈和库 rev 都可能已经漂移；任何移植都必须重新编译、重新测量、重新验收。

## 4. 分类口径

### 4.1 五类定义

| 分类 | 判定标准 | 典型证据 | 本审计中的例子 |
| --- | --- | --- | --- |
| 正优化（整帧） | FPS、帧间隔、p99 或长帧计数等用户可感知的整帧指标有稳定改善，且质量通过 | 同一 SO 的多轮 ABBA；低画质与普通画质至少一个方向一致；p99 或长帧计数改善；质量对照通过 | P-03 通用字体图集池 |
| 正优化（局部） | 上传量、HUD 尖峰、单一阶段墙钟或 draw call 明确改善，但整帧 FPS 基本不变 | 阶段计时、上传字节、draw call、单一窗口的 app wall 改善；整帧 FPS 在噪声内 | P-01 谱面预编译、P-02 尾工作集、P-05 block tiles、P-06 图集增量、P-07 Chart JSON 分片 |
| 无优化 | 改善在噪声内，或只有 API 调用数、理论上限改善，墙钟不变 | 多轮 ABBA 方向不一致；对照组漂移大于组差；只有微基准；整帧 FPS 与 p99 不变 | N-06 模型分帧、N-08 mask 局部优化、N-16 PBO |
| 负优化 | 主要指标变差，或质量、稳定性回归 | FPS 下降、app wall 上升、p99 或 max 变差、严格像素失败、崩溃或回退失败 | N-03 冻结文字、N-04 粒子 stream discard、N-05 UI 后台解码、N-07 glyph scoped flush、N-10 snapshot 回退 |
| 负优化（质量失败） | 质量门失败导致不可采用；性能可能未测，不能据此声称性能回归 | 严格像素失败、Case 未执行、无法进入普通路径 | N-15 固定纹理存储 app 侧 |

L 项的分类沿用 `library-level-optimizations.md` 的库级判定。库级的正确性修复归为“无优化（非性能）”，不等于整帧收益；“无”也不等于代码没有价值，只表示没有可归因的帧率或墙钟收益。

### 4.2 判定规则

- **整帧优先**：只要 FPS、帧间隔 p99、长帧计数中任何一项稳定改善，并且质量通过，就优先判整帧；不能因为“某个阶段只快了 0.5ms”而把整帧改善降级成局部。
- **局部不升级**：阶段墙钟、上传字节、draw call、纹理容量、缓存命中率的改善，只有在整帧指标也稳定改善时，才可以升级为整帧正优化；局部改善本身不等于整帧改善。
- **倍率不可跨层**：`render` 调用快 19 倍，不等于游戏快 19 倍；`upload` 少 50%，不等于帧时间少 50%。阶段倍率只能写在阶段结论里。
- **噪声判定**：对照组 A1/A2 的漂移绝对值大于处理组与对照组的差，或者处理组两次运行落在对照组两次运行之间，不能判正优化。
- **单窗口不外推**：一个谱面、一个 25 秒或 30 秒窗口、一个设备上的方向性结果，只能支持“这个窗口内”的结论；不能写成“所有谱面都更快”。
- **质量是否决项**：严格像素失败、未初始化 texel、透明边缘差异、字形覆盖错误，任何一项都足以把性能结论降为负优化或未完成。
- **先分类再解释**：不允许先写“有希望”，再挑一个指标证明它。先按主指标分类，再写限制和适用边界。

### 4.3 分类示例

| 情况 | 分类 | 理由 |
| --- | --- | --- |
| P-02 尾工作集：低画质 app wall 9.042→6.272ms（-30.64%），FPS 仍约 59.78 | 正优化（局部） | 阶段与 app wall 明确改善，但 60Hz 窗口内 FPS 没有变化 |
| P-03 字体池：普通画质 FPS 46.11→57.92，帧间隔 p99 48.53→20.88ms | 正优化（整帧） | FPS、帧间隔 p99、长帧计数同时改善，质量通过 |

## 5. 状态口径（核心）

### 5.1 只允许两个主线状态

| 主线状态 | 含义 | 何时使用 |
| --- | --- | --- |
| `☐ 未实施（main）` | Phira-Pro `main` 尚未合入该优化，或已合入但验收未完成 | 默认状态；任何未完成验收的条目都保持此状态 |
| `☑ 已实施（main）` | 已合入 Phira-Pro `main`，并完成质量验收与性能验收 | 仅在验收证据完整、验收人签字、普通路径确实使用该代码后使用 |

除此之外，没有第三种主线状态。部分完成、已合入但未验收、参考实现默认开、参考实现默认关、真机跑过但未复测，全部保持 `☐ 未实施（main）`。

这条规则的原因是：读者需要用一个布尔值判断“要不要在 main 上继续投入”。如果状态栏里混入“本地已写”“默认开启”“研究通过”等限定词，读者就无法判断主线是否真的拥有这项优化。

### 5.2 参考实现的两个维度

参考实现单独记录，不与主线状态混写。它有两个维度：实现完成度、默认开关。

| 维度 | 取值 | 含义 |
| --- | --- | --- |
| 参考实现状态 | `完整` | 有真实消费者，能编译，能在参考实现中运行；不代表 `main` 已合入 |
| 参考实现状态 | `原型` | 有代码或探针，但消费者、产品路径或验收链不完整；不能当作可直接移植的实现 |
| 参考实现状态 | `无` | 没有参考实现代码，只有设计或测量结论 |
| 参考实现默认 | `开` | 参考实现的普通构建或普通配置默认走该路径；不代表 `main` 默认走该路径 |
| 参考实现默认 | `关` | 参考实现默认不走该路径，需要显式开关或研究请求 |
| 参考实现默认 | `不适用` | 没有默认开关概念，或该条目只提供 API、自动机制、查询能力 |

两个维度必须分开写。一个条目可以是“参考实现状态：完整；参考实现默认：关；主线：`☐ 未实施（main）`”，这三件事同时成立，不能压缩成一句“已实现但默认关闭”。

### 5.3 禁止写法

| 禁止的主线写法 | 问题 | 应写成 |
| --- | --- | --- |
| 主线列写“参考实现完成” | 把参考实现当成了主线 | 主线 `☐ 未实施（main）`；参考实现状态 `完整` |
| 主线列写“默认开” | 默认开关是参考实现维度 | 主线 `☐ 未实施（main）`；参考实现默认 `开` |
| 主线列写“默认关” | 同上 | 主线 `☐ 未实施（main）`；参考实现默认 `关` |
| 主线列写“能编译”或“真机跑过” | 编译和跑通都不是验收 | 保持 `☐ 未实施（main）`，把事实写进参考实现状态 |
| 合入 `main` 但未验收就勾选 | 验收链缺失 | 保持 `☐ 未实施（main）`，备注“已合入，验收未完成” |
| 用“部分完成”勾选 | 部分完成不是主线完成 | 保持 `☐ 未实施（main）`，在条目内写实施进度 |

另外三条硬性禁止：

- 禁止在主线状态栏附加工作分支名、研究代号或本地检出名称。需要指代本地代码时统一写“参考实现”。
- 禁止把“参考实现默认开”当成“主线默认开”，也禁止把“参考实现默认关”当成“主线未实现”。
- 禁止用“参考实现的旧 ABBA”替代 `main` 构建上的验收证据。旧证据只能证明参考实现当时的表现，不能证明当前 `main` 的行为。

### 5.4 主线判定流程

1. 检查提交是否可从 `main` 到达：`git merge-base --is-ancestor <commit> main` 返回 0，或 `main` 中存在等价代码。不能到达就是 `☐ 未实施（main）`。
2. 检查普通构建、普通配置、普通运行路径是否真的使用该代码。只在研究开关、测试构建或微基准里出现的代码，不算主线路径。
3. 检查验收证据是否来自 `main` 构建。参考实现的旧数据、旧 SO、旧日志都不能直接充当主线验收。
4. 检查验收人是否独立于实施人，检查证据是否包含同一 SO、轮次、样本数、整帧指标和质量对照。
5. 以上全部通过，才写 `☑ 已实施（main）`；任何一项缺失，保持 `☐ 未实施（main）`。
6. 参考实现状态与默认开关单独填写，不参与主线布尔判断。

## 6. 实施完成后如何标记

### 6.1 条目顶部只改一个方框

每个条目在详细文档中的顶部必须有一行状态框，且只能是以下两种之一：

```markdown
☐ 未实施（main）
```

```markdown
☑ 已实施（main）
```

合入 `main` 并完成验收后，把 `☐ 未实施（main）` 改成 `☑ 已实施（main）`。不要使用任何第三种状态框；部分完成保持 `☐ 未实施（main）`，在条目内写“实施进度”。

### 6.2 必填字段

`☑ 已实施（main）` 下方必须填写以下字段，缺一不可：

| 字段 | 格式 | 要求 |
| --- | --- | --- |
| 实施日期 | `YYYY-MM-DD` | 代码在 `main` 生效的日期，不是文档修改日期，也不是参考实现的首次提交日期 |
| 实施提交 | 40 位完整 SHA | 必须是 `main` 上的实际落地提交；cherry-pick 或 squash 时写最终落地提交 |
| 实施人 | 姓名或稳定 ID | 不用“团队”代替个人 |
| 验收人 | 姓名或稳定 ID | 不能由实施人自己验收；独立审计可写“独立审计（记录名）” |
| 验收证据 | 内联数据 | 至少包含同一 SO、轮次、样本数、整帧指标、质量对照；必须来自 `main` 构建 |
| 验收结论 | 一句话 | 写“整帧/局部/无/负/未完成”，与分类口径一致 |
| 差异说明 | 可选 | 实现与原始提案不一致时必填，写清差异和原因 |

验收证据不能只写“通过”“更快了”“和参考实现一致”。必须写方向、数值、单位、比较对象和测量条件。例如写“普通画质 app wall 11.158→9.810ms（-12.08%），FPS 46.115→57.917，10 组 RGBA 逐通道相同”，而不是只写“字体池有效”。

### 6.3 勾选与不勾选

- **只合入未验收**：保持 `☐ 未实施（main）`，在条目内写“已合入，验收未完成”。不得勾选。
- **验收失败**：保持 `☐ 未实施（main）`，写失败指标、失败条件、是否可回退。不得把失败条目改成正优化。
- **部分完成**：保持 `☐ 未实施（main）`，写清哪些子项已完成、哪些没有真实消费者、哪些没有质量证据。
- **回滚**：从 `☑ 已实施（main）` 改回 `☐ 未实施（main）`，保留原实施日期和提交，新增“回滚记录”，写回滚提交、回滚原因和影响范围。不要删除历史。
- **重新验收**：回滚后再次落地，重新填写实施日期、实施提交和验收人；不要复用上一次的验收证据。
- **参考实现证据**：只能作为参考实现的背景，不能直接充当 `main` 验收证据。必须在 `main` 构建上重新测量。

## 9. 阅读顺序、置信度与已知限制

### 9.1 阅读顺序

1. **本文件**：先建立一句话口径、范围、分类、主线两态、参考实现两维和标记流程。
2. **`positive-optimizations.md`**：看 7 项值得做的候选，确认收益、证据、风险和落地条件。
3. **`non-positive-optimizations.md`**：看 17 项否决或未完成方案，避免重复踩坑。
4. **`library-level-optimizations.md`**：如果优化需要改 macroquad 或 miniquad，先读库级契约、默认值和回退条件。
5. **`appendix-mainline-integrated.md`**：确认哪些早期优化已经在 `main`，避免把已完成机制重新立项。
6. **`appendix-methodology.md`**：最后读测量协议、证据等级、复现方法和术语表；实施与验收前必须读。

如果时间有限，至少读本文件的第 1、5、6、7 节，以及目标条目对应的详细文档。第 5 节决定“能不能勾选”，第 6 节决定“怎么勾选”，第 7 节决定“当前有哪些条目”。

### 9.2 置信度

| 置信度 | 定义 | 何时算高 |
| --- | --- | --- |
| 高 | 结论足以支持工程决策，外推范围有限但方向稳定 | A 级证据；至少两个独立 cohort 或低/普通画质方向一致；对照组漂移小于组差；质量通过；真实消费者存在 |
| 中 | 结论可信，但只覆盖一个窗口、一个画质或一个阶段 | B 级证据；同一 SO 的 ABBA；方向明确；但未覆盖全曲、全 UI、多设备 |
| 低 | 只能说明“值得再看”或“不要做”，不能支持收益承诺 | C/D 级证据；或 B 级但方向与覆盖不足以支持决策，例如 ring 无收益、单窗口无复现、原型缺少整帧对照 |

“高”不是“所有设备都成立”。它只表示：在文档写明的设备、谱面、窗口和质量配置下，结论足够稳，可以作为实施依据。置信度高也不改变主线状态；一项优化可以“置信度高、参考实现完整、默认开”，同时“主线未实施”。

### 9.3 证据等级

| 等级 | 定义 | 本审计中的例子 |
| --- | --- | --- |
| A | 同一 SO 多轮 ABBA，至少 4 轮；有像素或质量对照；有真实消费者；检查对照漂移 | P-02、P-03、N-05、N-10 |
| B | 单窗口、单谱面、局部阶段，或只有一种画质；同一 SO 的 ABBA 或成对对照 | P-01、P-05、P-06、P-07、N-01、N-02、N-03、N-04、N-06、N-07、N-08、N-09、N-11、N-12、N-13、N-14、N-16、N-17 |
| C | 只有微基准、单元测试、`glFinish` 诊断或单次探针；没有真实消费者或没有整帧对照 | N-15 |
| D | 没有数据，只有原型或设计 | 本索引没有 D 级结论；D 只用于设计稿，不进入总表 |

A 级证据不自动等于高置信度。还要看方向是否在低/普通画质一致、对照组漂移是否小于组差。B 级证据通常给中置信度；如果同一结论在多个 B 级 cohort 重复，可以升为高；如果只有空结果、单窗口无复现或原型缺少整帧对照，则给低。C 级证据只能给低置信度，不能用于整帧正优化结论。

### 9.4 已知限制

| 限制 | 表现 | 对结论的影响 |
| --- | --- | --- |
| 单设备、单谱面、单窗口 | 大多数 A/B 在一台 Mali-G52 MC2 设备、一个谱面、25 秒或 30 秒窗口上完成 | 不能外推到所有 GPU、所有谱面、整曲、完整 UI、暂停/恢复/seek |
| 文档与代码默认值冲突 | `chart_pre_compile` 编译包含但运行默认 false；`font_atlas_pool` 主池开但子项关；`async_chart_json` 普通构建开、研究请求关；`line_elision` 默认 true；`block_tiles` 研究请求 false | 以普通构建、普通配置的实际行为为准；正文同时写“编译包含”和“运行默认” |
| 参考实现与 `main` 接口漂移 | 参考实现落后 `main`，配置字段、场景栈、资源路径和库 rev 都可能不同 | 不能直接 cherry-pick；必须重新配对库 rev、重新编译、重新测量、重新验收 |
| 驱动等待混入 app wall | `app wall`、`render`、`swap` 都包含驱动等待和调度 | 不能把 app wall 当纯 GPU 时间；不能把阶段倍率当帧率倍率 |
| 质量对照只覆盖采样帧 | 末帧 RGBA 相同不等于所有时刻、所有视角、所有自定义材质都相同 | 质量结论限定在采样条件；需要多时刻、多配置对照 |
| 库 rev 不一致 | `main` 与参考实现使用的 macroquad、miniquad pin 不同 | 只替换一个 rev 可能编译失败或行为不同；两个库必须配套升级 |

## 10. 术语表

| 术语 | 简短含义 |
| --- | --- |
| app wall | `update + render + flush` 的 CPU/driver 墙钟，包含驱动执行、调度与等待，不包含 swap，也不等于纯 GPU 时间 |
| frame interval | SurfaceFlinger 真实呈现时间戳之间的间隔；和 app wall 不是同一个口径 |
| chart stage | 谱面更新与绘制阶段的墙钟，是 app wall 的一个子集，不等于整帧 |
| managed draw | 通过 macroquad 管理路径提交的 draw call，不是 raw GL 调用 |
| workset | 为当前窗口预先计算、运行时必须遍历的音符或几何集合 |
| tail | 当前时间之后、仍会被遍历但可能已经出屏的音符尾部 |
| line DCE | 在默认材质、透明线、无深度、无 capture 等守卫下，删除最终 alpha 为 0 的判定线绘制 |
| atlas pool | 多张完整 RGBA 图集版本加 fence 轮换的字体图集池 |
| atlas delta | 以 32×32 tile 记录修改 generation，只上传变化矩形的增量机制 |
| atlas crop | 只发布图集实际使用高度，而不是整张 2048² 图集的裁切方案 |
| PBO | pixel unpack buffer；先把像素写入 GPU 缓冲，再从缓冲上传到纹理 |
| immutable storage | 用 `glTexStorage2D` 固定尺寸和格式的纹理存储；可以子更新，不能 resize |
| uniform cache | 按 shader program 和 uniform 字段记录上次值，跳过重复 `glUniform*` 调用的缓存 |
| snapshot fallback | snapshot、blit 或 shader copy 无法复现原采样结果时的回退路径 |
| same SO | 同一份 `.so`；用于排除“换了构建”带来的差异 |
| ABBA | 同一轮内按 A-B-B-A 交错运行处理组与对照组，避免时间漂移被当成收益 |
| strict RGBA | 逐通道完全相等，包括 alpha 为 0 时的 RGB |
